## Stack

Spring Boot 3.4.x on Java 21, Postgres, React + Vite, Monaco editor, run locally and reached over a tailnet.
Java 21 on `PATH` and Docker are required for local development; see `README.md` for the run and test commands.

## Layout

One repo, two toolchains, each left to own its usual root rather than nested under a shared build tool:

- `backend/` - Spring Boot, Maven (`./mvnw`). Own package tree starts at `com.sweprep.backend`.
- `frontend/` - React + Vite, npm.
- `docker-compose.yml` at the repo root - Postgres for local dev, disposable and reproducible. Maps to host port 5433, not 5432, so it doesn't collide with any other local Postgres already running on the machine.
- `test.sh` at the repo root - the one documented command that runs both suites.

## Local dev topology: port, proxy, CORS (issue #34)

The frontend dev server (`frontend/vite.config.ts`) is pinned with `strictPort` (fails loudly if `:5173` is taken, rather than silently moving to `:5174` and leaving every API call refused with nothing explaining why) and bound to every interface with `host: true`, so it's reachable from another device over the tailnet at `http://<tailnet-host>:5173` exactly like `localhost:5173`. It also proxies `/api` and `/actuator` to the backend, so the browser's calls are same-origin regardless of which of those addresses loaded the page - `App.tsx`'s `API_BASE_URL` defaults to `''` for this reason, not a backend URL. CORS is therefore not load-bearing for the app's own calls in dev; it still matters for anything that talks to the backend directly. That config is `sweprep.web.allowed-origins` (`backend/src/main/java/com/sweprep/backend/web/WebConfig.java`), a single comma-separated property also referenced by the actuator's own CORS config in `application.yml` - one source, not two hardcoded literals. Every fetch in `App.tsx` goes through the `apiFetch` wrapper, which turns the browser's undescriptive `TypeError: Failed to fetch` (thrown alike for a down backend, a network failure, or a CORS block) into a message naming the target URL and the likely cause, so a blocked or failed call is never a silent blank screen.

Schema migrations use Flyway (`backend/src/main/resources/db/migration/`), never Hibernate `ddl-auto`, starting from the very first migration. This is a hard invariant, not a style preference - see issue #12.

Backend tests spin up a real, disposable Postgres via Testcontainers rather than mocking the datasource. The `api.version` system property pinned in `backend/pom.xml`'s surefire config is a workaround for the dev machine, not stray config: Testcontainers' Docker connectivity probe hardcodes an old API version that this machine's Docker Engine (new enough to enforce a stricter MinAPIVersion) rejects outright, so without it the probe fails before ever checking what the daemon supports. Don't remove it. It's confirmed *unnecessary* on GitHub Actions' hosted `ubuntu-latest` runners (Docker Engine 28.0.4 there accepts the hardcoded probe version fine) - keep the pin anyway, since it's harmless where it isn't needed and required on this box.

CI (`.github/workflows/ci.yml`) runs `./test.sh` on every push and pull request, on GitHub-hosted `ubuntu-latest` runners with Docker preinstalled - so the backend's Testcontainers suite genuinely runs there, not just locally.

## Execution: exercise to verdict

The seam that runs a submission lives under `backend/src/main/java/com/sweprep/backend/` in five packages: `exercise` (language-neutral model), `content` (loading), `language` (adapters), `runner` (execution) and `grader` (pass/fail), wired to the editor by `web`.
Issue #13 established the runner/adapter shape; issue #14 made the domain model real and turned on content loading.

An `Exercise` (issue #14) carries prompt, `domain`, `topics`, `Difficulty`, a `Form` (`REP` vs `CHALLENGE`, an attribute never a subtype), a `Response` spec (how it is answered) and a `Grading` spec (how it is judged). `Response` and `Grading` are independent sealed interfaces: `Response.Code` carries a `Signature`, `Response.Choice` a list of `Option`s (each a text plus, for a distractor, the misconception it targets - issue #42); `Grading.TestCases` carries cases + a `Comparison`, `Grading.AnswerKey` a fixed expected value. A coding problem is Code+TestCases; a concept question is Choice+AnswerKey - but a code response judged by an answer key (predict-output) is valid, which is why the two are not one choice. `AnswerKeyGrader` compares the submitted answer against the expected value under the exercise's `Comparison`, trying both the raw text and, when the submission is valid JSON, its parsed form, so string, numeric, and structured answer keys all grade correctly and a multiple-choice option that looks like JSON (`true`, `1`) is never mis-graded against a string answer key.
The sealed hierarchies were extended once already (design revision t3, ticket T1): `Response.FreeText` (a text box, no fields) and `Grading.SelfCheck(modelAnswer)` add the self-graded produce-then-reveal format, and `Exercise` gained three content-level tags - `family` (a `List<Family>`; the closed role-family taxonomy the family filter selects on), `stability` (`STABLE`/`VOLATILE`, default `STABLE`) and a nullable `reviewed` date - all parsed by `ExerciseParser` and all optional in the JSON (an added 10-arg convenience `Exercise` constructor defaults them). These are content-JSON fields, not DB columns, so T1 needed no migration.
Issue #46 then landed the sealed `Content` supertype (`exercise` package) that the concepts spec settled on: `Content permits Exercise, Lesson` carries the metadata both kinds share (id, title, statement, domain, topics, difficulty) plus the three content-level tags, which were hoisted here from `Exercise` so they live in one place - `Exercise implements Content` additively (it already had every accessor), and `Lesson` is its sibling.
A `Lesson` is **read, never attempted**: it has no `Response` and no `Grading` by design, so a lesson can never be graded or produce a verdict - the type is the boundary, not a caller check - and it references its `checks` (the `Form = REP` exercises that verify it) by id.
The loader (`FileExerciseCatalog`) now satisfies two seams: `ContentCatalog` (`allContent`/`contentById`, every loaded item) and the unchanged `ExerciseCatalog` (`all`/`byId`, filtered to exercises, the seam that attempts and grades), so a lesson never reaches the grade path.

Contracts, kept deliberately apart (see the map, issue #6):

- `LanguageAdapter` generates both the editor stub and the harness from a `Signature`; neither is hand-written per problem.
- `Runner` only compiles and executes (`ExecutionRequest` to `ExecutionResult`) and knows nothing about test cases or verdicts.
- `Grader` is polymorphic over the grading spec: each declares `supports(Exercise)` and `GraderRegistry` routes each exercise to the one that handles it. `TestCaseGrader` runs code; `AnswerKeyGrader` compares a submitted answer to a fixed value and has **no `Runner` dependency at all** - the demonstration (issue #14) that grader and runner are separate pieces. `COMPILE_ERROR`, `TIMEOUT`, a test failure and an `ERROR` (ran but reported no result) are distinct outcomes. `SelfCheckGrader` (design revision t3, T1) goes further: it is a routed `Grader` bean (`supports` a `Grading.SelfCheck`) with no runner and **no verdict** - its `grade` deliberately *throws*, and a separate `reveal(Exercise)` hands back the model answer. The boundary that a self-check never emits a machine verdict (so a self-rating can never reach the SRS quality score) lives in the type, not in callers; `GraderRegistry.grade` on a self-check therefore throws, and the produce-then-reveal flow that records the self-rating is a later ticket (T5).

Comparison is the grader's job, not the harness's (issue #31). The harness only records each case's raw return value; the grader compares it to the expected value under the exercise's declared rule.

- A grading spec declares a `Comparison` (`exercise` package): a sealed interface with `exact`, `orderInsensitiveSequence` and `setEquality`, defaulting to `exact`. A problem-specific rule is added by adding one more permitted implementation, not by redesigning - so extend it there rather than reaching for per-content workarounds. Two Sum declares `orderInsensitiveSequence` instead of pinning an order in its statement; 3Sum declares `setEquality` (with each triplet still stated ascending, so its elements compare exactly).
- All rules share `JsonEquality.equal`, which compares numbers by magnitude (`decimalValue().compareTo`), so `5`, `5.0` and a wider int type are one answer. Never compare answers with Jackson's `JsonNode.equals` - it keys on the concrete node type and fails numerically-equal answers.

Sharp edges worth knowing before touching this:

- The harness classpath is resolved from the `CodeSource` of the Jackson classes it imports, not from `java.class.path`, because Surefire may hand the JVM a booter jar instead of the real dependency jars. See `JavaLanguageAdapter.jacksonClasspath`.
- The harness writes each case's result to a dedicated file (an `ExecutionRequest.outputFiles` entry the runner reads back), never to the submission's own stdout. This is deliberate: stdout is capped at 1MB (`LocalJavaRunner.MAX_CAPTURED_BYTES`, keep it) to stop a runaway print loop exhausting the backend heap, and putting the result on that same channel let a noisy-but-correct solution truncate away its own result.
- The execution timeout is `sweprep.grader.timeout` (default `PT10S`); the local runner is unsandboxed by design (single user, issue #2's swap point).

## Content: private, loaded from a local path

Problem content lives only in the separate private repo `swe-prep-content`, never here (public-engine/private-content, issues #4/#14).
`FileExerciseCatalog` (`content` package) reads every top-level `*.json` in `sweprep.content.path` (default `../content`, gitignored `/content/`; override with `SWEPREP_CONTENT_PATH`), parsing each with the hand-rolled parsers so every failure names the file and field. See `swe-prep-content/README.md` for the on-disk format.
`ContentParser` reads a top-level `"kind"` discriminator (default `"exercise"`, so every pre-lesson file loads unchanged) and dispatches to `ExerciseParser` or `LessonParser` (issue #46). The two parsers share the metadata reads (`requireText`, enums, `topics`/`family`/`stability`/`reviewed`) through the package-private `ContentJson`; a malformed lesson fails naming its file and field exactly as a malformed exercise does, its message reading `Malformed lesson content in ...`.

- Loading is lazy and cached; a *failed* load is not cached, so cloning content after boot works without a restart. Missing path, malformed file, duplicate id, etc. all surface as `ContentException`, mapped to a 500-with-message by `ContentErrorHandler` so the editor shows a clear error.
- **Competitive-distractor gate (issue #42).** A choice's options are `Response.Choice`'s `List<Option>`, each `Option(text, misconception)`; a distractor (a wrong option) must name the specific misconception it targets, the correct option names none. `ExerciseParser.validateDistractors` enforces this *mechanically* at load: for every `Choice + AnswerKey` it finds the correct option by the grader's own match rule (`Comparison`, raw + parsed-JSON, so the classification matches how a submission grades), then rejects any distractor with no declared misconception - and rejects an answer key that matches no option - as a `ContentException` naming the file, the option and the rule. The JSON accepts a plain string (option, no misconception) or `{ text, misconception }`; a bare-string *distractor* therefore fails the gate. The misconception is authoring/verification metadata (the topics report's "Claims Ledger"), **never shipped to the learner** - `ExerciseView`/`ResponseView` send only `optionTexts()`, like the withheld explanation and model answer. This is the *declared* half (machine-checkable); whether a misconception is genuinely *plausible* is the human red-team judgement the authoring checklist in the private `swe-prep-content` repo owns (a separate PR, alongside the on-disk format doc). `FileExerciseCatalogTest` demonstrates a passing set and a deliberately bad giveaway set failing.
- **Answer-shape tells are a separate, set-level concern from #42 (issues #59/#60).** The distractor gate judges each option in isolation; it cannot see that the correct answer is always in slot 1 or always the longest - a property of the option *set*. Two defenses close that, neither in the loader (an author bias is a quality smell, not corruption). Position (#59): `web/OptionShuffler` + `DeterministicOptionShuffler` re-order options at serve time in `ExerciseView`, seeded on (exercise id, user id, calendar day - the injected `SessionConfig` `Clock` + `CurrentUser`). The day is in the seed on purpose: under spaced repetition a learner meets a check many times, so an id-only seed would fix the answer in one slot forever and just move the position tell onto a slower clock; folding in the day rotates the order between sittings while keeping it stable within a day (refresh/resume/re-queue), with nothing persisted (options render before an attempt exists). Grading is by text (`AnswerKeyGrader`), so order never affects correctness - the seam is injectable for exact-permutation tests rather than switched off. Length/qualifier (#60): `content/AnswerTellChecker` (pure) flags a correct option longer than `DEFAULT_LENGTH_RATIO` (1.3x, tunable) times the distractor mean, plus a lone hedged option among absolutes; it runs in `RealContentSmokeTest` (CI-skipped, so the *expected* real-content failure never wedges CI) and is demonstrated both ways by fixtures in `AnswerTellCheckerTest`. Both find the correct option via `content/ChoiceKeys` - the one place the AnswerKey match rule lives, shared with `ExerciseParser`. The #60 authoring-doc update is a **separate PR in `swe-prep-content`**. Connective style (#65): the same `check()` also flags a correct option that is the *only* one carrying a causal connective ("since", "because", "so that" - `AnswerTellChecker.CONNECTIVES`, one place, easy to extend) and, with equal severity (same `Tell.CONNECTIVE_STYLE`), the mirror case where it is the only one *lacking* one. This is checked **one lexeme at a time, never merged into one "has some connective" bucket** - a corpus audit found a merged-bucket version blind to a real regression where every key said "because" and every distractor said "since" (both sides read as "has a connective" to the merged version). `as` was in `CONNECTIVES` at #65's launch (it names the lexeme explicitly) but was dropped in #69 once measurement replaced the guess: over the 29 real four-option items in production content, `as` caused 3 of the axis's 4 flags and *every one* of those 3 was a false alarm (comparison "as well as", labelling "flags it as positive"/"treated as stale"/"known as", temporal "as the world changes") - a full scan of every `as` occurrence in that corpus found zero genuine causal uses to weigh against them, so a causal-context heuristic (only count sentence-initial "As " or ", as ") had nothing left to preserve and simply dropping the lexeme won out. `CONNECTIVES` is now `since`/`because`/`so that`; the genuine catch in the same measurement (a "because" tell where every distractor opened with "Because" and the key did not) is untouched, since it never depended on `as`. The regression fixture for #65 is the real swe-prep-content PR #5 batch at its pre-fix commit, extracted at test time via `git show` into a temp dir (never committed here) by a dedicated `RealContentSmokeTest` test, skipped like the others without a local clone; #69's fixtures are synthetic (`AnswerTellCheckerTest`, quoting the real corpus wording behind each false alarm) rather than `git show`-extracted, since the fix is engine-side with no content-repo commit to diff against. Length axis, extended (#67): the ratio check now runs against **word count as well as characters**, and is **two-sided** (a ratio of 1/1.3 fails exactly like 1.3, not just "too long"). It also gained a **rank** check - the correct option flagged for being the unique shortest/longest option outright, independent of the ratio bar, since a key can sit comfortably inside 1.3x and still be the only one at an extreme. Rank is deliberately checked on **word count only, not characters**: character count is close to continuous prose, so two independent sentences almost never land on the same value, and a corpus measurement found raw character-rank flagging a majority of already-balanced, hand-reviewed content (including this repo's own "roughly balanced" fixture) purely from that noise - the false-alarm failure mode issue #69 named. Word count is coarse enough that ties are common and a unique extreme is a real, human-perceptible signal, matching what the production exploit ("guess the shortest option by word count", 41.2%/36.0% against a 25% baseline) actually measured. Passing never requires uniform option length - the guidance is always "must not be a unique extreme," never "make them all equal," so a tie at the extreme (including the degenerate all-equal case) passes without being required. The regression fixture is the real `http-status-classes`/`cache-no-cache-vs-no-store` items at their pre-fix commit in swe-prep-content history, same `git show`-into-temp-dir pattern as #65's fixture.
- **Never commit problem content here.** `scripts/check-no-content.sh` fails CI and `./test.sh` if any is (tracked `content/`, un-ignored `content/`, or tracked JSON matching either leak shape (issue #46): an exercise carrying both `"statement"` and `"grading"`, or a lesson carrying `"kind":"lesson"` or both `"statement"` and `"checks"`). The guard has its own tests in `scripts/check-no-content.test.sh`, also run by `./test.sh`. Backend tests use synthetic fixtures (`testsupport/Fixtures`, temp-dir JSON); the real seeded set is only exercised by `RealContentSmokeTest`, which *skips* when no local clone is present.
- Person-owned tables carry a `user_id` and exactly one user is seeded (migration `V2__app_user.sql`); `app_user` is the person table its own PK is that id.

## Content authoring: from problem to reps (issue #24)

The practical gate on daily usability: the `authoring` package derives a problem's warm-up reps mechanically rather than having an author hand-write five items per problem, closing the gap issue #9 named ("reps are a content-authoring problem roughly the size of the main problem set"). One content pile, not two - authoring a problem produces its reps, the author verifies rather than writes them from scratch. The single command is `scripts/author-content.sh <problem-spec.json> [content-dir] [--yes]`, wrapping `mvn -q compile exec:java -Dexec.mainClass=com.sweprep.backend.authoring.AuthorContentCli` (an `exec-maven-plugin` execution added to `backend/pom.xml`, not bound to any lifecycle phase, so `./mvnw test`/`./test.sh` never invoke it).

- **The authoring unit is `ProblemSpec`** (`ProblemSpecParser`): statement, cases, a reference solution, and optionally an input generator - the same shape as a `CHALLENGE` exercise's JSON, with `response`/`grading` flattened to the top level and one authoring-only field, `referenceSolution`, added. Deliberately close to the real format (an author who knows `swe-prep-content/README.md` already knows this one) and deliberately *not* shaped like a real exercise JSON: it can never carry both `"statement"` and `"grading"`, so a problem-spec fixture committed as a test resource could never trip `scripts/check-no-content.sh`'s leak-shape grep.
- **Every derivation is mechanical, not LLM-drafted**, matching the ticket's "deterministic where possible" instruction with no provider dependency:
  - *Pattern-identification* comes from the **statement's own declared `topics`** (per issue #9), not the solution - `PatternCatalog` maps a recognised topic tag to a canonical pattern label and picks distractors (with misconceptions) from the rest of a fixed catalog; an unrecognised topic set skips the rep rather than guessing. Available cold (`derivedFrom` null), matching the pre-existing warm-up rule that pattern-ID needs no prior attempt.
  - *Complexity* comes from `ComplexityHeuristic`, a structural estimate (max `for`/`while` nesting depth, with one pattern - `/ 2`, `>>= 1`, etc. inside a depth-one loop - recognised as logarithmic). Recursion (the method's own name followed by `(` occurring more than once anywhere in the source - robust to both conventional and single-line formatting) or nesting past cubic is *refused*, not guessed: `estimate` returns empty and the rep is skipped.
  - *Fill-in-the-blank* and *spot-the-bug* both draw from `MutationCatalog`, a fixed, pure catalog of single-line text mutations (relational-boundary, equality, logical, increment, arithmetic-offset, literal-bump), gated so the relational/equality/logical operators only touch a line that plainly opens a conditional (`if (`/`while (`/`for (`) - the guard that keeps them off a generic type parameter's `<`/`>`. `candidates(source)` enumerates every mutation in a fixed, deterministic order (ascending line, then catalog order); nothing in this class executes anything.
  - *Spot-the-bug*'s winning mutation is the **first candidate that both compiles and empirically fails a declared case**, verified by re-running it through `ReferenceExecutor` - the same `JavaLanguageAdapter`/`LocalJavaRunner` pair (plain, dependency-free `@Component`s, instantiated directly with no Spring context) that grades a learner's own submission. The correct option's text is generated from that mutation's line-and-diff (`"Line N was changed from `X` to `Y`."`, `MutationCandidate.describe()`) - issue #24's "mutation recorded as the answer" is met literally, not just in spirit. Distractors are *other* candidates' `describe()` text, false by construction (only the winning mutation was actually applied).
  - *Fill-in-the-blank* blanks one line and offers its `MutationCatalog` variants as distractors, but each variant is held to the **same empirical gate spot-the-bug uses**: `RepDeriver.verifiedBreakingVariants` re-runs every candidate through `ReferenceExecutor` and keeps only those whose mutated source actually breaks a declared case (a compile error, a timeout, or any failing case all count), so a behavior-preserving mutation can never slip in as a silent second correct answer. The rep is skipped unless a single line yields three such verified-breaking variants.
  - *Predict-output* actually **runs** the reference solution (`ReferenceExecutor.callOnce`) on its own smallest declared case and uses the real returned JSON value as the answer key - never a value copied from the hand-authored case by coincidence.
  - Every rep type a run could not confidently derive is *skipped and named* (`RepDeriver.DerivationResult.skipped()`), never silently filled with a guess - the human-verification step downstream is what makes an imperfect heuristic safe to ship at all.
- **The reference solution is verified before anything is derived.** `RepDeriver.derive` first runs it through `ReferenceExecutor` against every declared case; a compile error, a timeout, or a failing case throws `AuthoringException` naming the problem id, and nothing downstream runs. This is the same empirical bar every mutation is later held to.
- **Human verification is a real gate, not a courtesy message.** `ReviewPresenter` prints the challenge, every derived rep (statement, every option with its correct/distractor status and misconception, the answer key, the explanation), what was skipped and why, and an `AnswerTellChecker` sweep (issue #60/#65/#67 - the same check `RealContentSmokeTest` runs against real content) over the whole derived set. `AuthorContentCli.author` writes nothing until that review is accepted at an interactive prompt (`--yes` skips only the prompt, never the printed review, and is documented as a scripted/CI escape hatch, not the normal authoring flow).
- **`SafetyGuard` refuses a destination inside this public repo** (issue #24's fifth criterion) before any of the above runs. It locates this repo's own root from where the running class was loaded (its `CodeSource`), walking up to the directory carrying this repo's own layout signature (sibling `backend/`/`frontend/` plus `docker-compose.yml`) - not from the process's working directory, which a caller could have started anywhere. An environment where that root cannot be found at all fails **closed** (refuses) rather than skipping the check.
- **Output**: on accept, `ContentWriter` writes the challenge and every derived rep as `<content-dir>/<id>.json` in exactly the shape `ExerciseParser` reads (never through Jackson data-binding on the sealed `Response`/`Grading` hierarchies, which cannot round-trip them directly - a hand-rolled writer mirroring `ExerciseParser`'s own hand-rolled reads), plus the reference solution to `<content-dir>/solutions/<id>.java`, matching the convention the seeded real content already uses. Before writing, `AuthorContentCli.requireNoCollisions` refuses to silently clobber any path this run would create - every `<id>.json` **and** the `solutions/<id>.java` file - throwing `AuthoringException` rather than overwriting. `AuthorContentCliTest`/`ContentWriterTest` load everything written back through the real `FileExerciseCatalog` to prove the two never drift apart. This tool never commits, pushes, or opens a PR - content changes land in `swe-prep-content` as their own PR, by hand, exactly as every other content change does.
- All of this package's own tests are synthetic, non-real problems (a running-max, a linear-search-shaped demo, matching `testsupport/Fixtures`' convention) - never real interview content (issue #4/#14).

## SQL domain: a second domain on the same seam (issue #25)

The first proof the domain seam from decision issues #6/#10 is real, not aspirational: SQL landed by adding one more permitted `Response`/`Grading` record each, with **no change** to `Exercise`, `Grader`, `AttemptService`, the session loop, or `Verdict`'s outcome enum. `Response.Query()` is a marker like `FreeText`; `Grading.ResultSet(fixture, expected, comparison)` carries which fixture schema to run against, the expected rows (a JSON array of rows, each row itself a JSON array of column values **by position** - column names are never compared) and the *existing* sealed `Comparison` (`exercise` package), reused completely unchanged - `orderInsensitiveSequence()`/`exact()` already do exactly the right thing on an array of row-arrays via the shared `JsonEquality` primitive, including numeric-magnitude and `NULL` agnosticism, so nothing needed touching there. `ResultSet`'s compact constructor defaults `comparison` to `orderInsensitiveSequence()` (the opposite default from `TestCases`/`AnswerKey`), since SQL row order is otherwise unspecified unless the exercise's own statement asks for an `ORDER BY`. A SQL exercise carries no complexity target by simply never setting one - `Exercise.complexityCheck()` was already nullable and independent of the response kind, so this needed no special-casing anywhere, which is itself the acceptance criterion.

- **Execution: `sql` package, mirroring `runner` conceptually but not by interface.** `SqlRunner` (`execute(SqlExecutionRequest) -> SqlExecutionResult`) plays the same architectural role as `Runner` - only executes, decides nothing - but is its own interface rather than an implementation of `Runner`, since that one is shaped around compiling and running a program (source files, exit code, captured stdout) and a SQL query's shape (one query string in, a result set or a database error out) does not fit it. `PostgresSqlRunner` is the one implementation: it opens a JDBC connection to a **separate fixture database** on the same Postgres instance, sets `Connection.setReadOnly(true)` **and** connects as a dedicated Postgres role with `SELECT`-only grants (`sweprep.sql.reader-username`, belt and suspenders - either alone already refuses a write), restricts `search_path` to the exercise's fixture schema, runs the submission with `Statement.setQueryTimeout`, and **always** rolls the transaction back in a `finally` - success or failure, nothing a submission does is ever persisted. A `DROP`/`UPDATE`/etc. is refused outright by Postgres (a `SQLException` naming the read-only violation or the missing grant), reported back as `SqlExecutionResult.Outcome.QUERY_ERROR` - refused, never silently allowed and undone. Column values are converted by declared JDBC type (`NUMERIC`/`INTEGER`/etc. to a JSON number node, `NULL` to `NullNode`, dates/timestamps to ISO text), not left to Jackson's default `valueToTree`, which is what makes numeric-type and `NULL` normalisation actually hold.
- **Provisioning: `SqlFixtureProvisioner`, idempotent and lazy like `FileExerciseCatalog`.** On first use it creates the reader role and the fixture database (`CREATE ROLE`/`CREATE DATABASE`, cluster-wide operations any connection to the same instance can issue - no separate administrative connection needed) over the app's own datasource, then per named fixture creates its Postgres schema and runs its DDL-plus-seed script from content **once** (checked via `information_schema.tables`, so a shared schema persists across restarts rather than being reloaded every boot - "a schema is learned once" per decision #10) and grants the reader role `SELECT` on it. **Sharp edge:** the app's own connection details cannot be read via `@Value("${spring.datasource.*}")` in a Testcontainers test - `@ServiceConnection` wires a `JdbcConnectionDetails` bean the autoconfigured datasource consumes directly, never touching those properties, so reading them sees a stale default instead of the container's real user/port. `AdminConnection` casts the injected `DataSource` to `HikariDataSource` and reads `getJdbcUrl()`/`getUsername()`/`getPassword()` instead, which is correct in every environment (docker-compose, a real deploy, or a test container) with no environment-specific branch. A provisioning failure surfaces as `SqlFixtureException`, mapped to a 500-with-message by `SqlErrorHandler` (the same pattern as `ContentErrorHandler`) - distinct from an ordinary refused or timed-out submission, which is a `SqlExecutionResult` outcome and never an exception.
- **Content: `SqlFixtureCatalog` (`content` package), sibling to `FileExerciseCatalog`.** Reads `sql-fixtures/{fixture}.sql` (plain DDL + seed `INSERT`s for one shared schema) from the same `sweprep.content.path` clone exercises load from - no separate gitignore entry needed. `ExerciseParser` validates a `resultSet` grading's `fixture` name against `[a-z][a-z0-9_]*` at load time, since it is later concatenated into DDL/DCL identifier positions (`SqlIdentifiers.quoteIdent`) that cannot be JDBC-bind-parameterised - safe only because it is trusted, author-controlled content, gated by this check. Two or three shared, realistic schemas (decision #10) are content, like everything else in this list - authored in the private `swe-prep-content` repo, never here; see its README for the `query`/`resultSet` JSON shape (documented additively there for this ticket, coordinating with issue #24's concurrent content-tooling work on the same file).
- **Grading: `SqlQueryGrader` (`grader` package).** Applies the fixture (via `SqlRunner`), compares the returned rows against `expected` under the exercise's `Comparison`, and reports `Verdict.rows(matches, actualRowCount, expectedRowCount)` - a verdict factory distinct from `Verdict.of` because outcome here cannot be derived from `passed == total` (a wrong query can coincidentally return the right row *count* with wrong content). The disclosed failure signal is deliberately that bare row count and nothing else - never which rows differed or how - matching withhold-by-default judging (issues #16/#5) exactly the way `TestCaseGrader` withholds a failing case's values. `firstFailingCase` is left at its default (empty): there is no richer detail being held back for SQL to reveal on request.
- **Frontend: `Practice.tsx` renders `query` alongside `code`, not through a parallel surface.** The Monaco editor branch, the Run button label, and the code-vs-choice submission-value ternaries all widened to include the `query` response kind (Monaco's built-in `sql` language mode, no extra install); `VerdictView` takes a `unit` prop (`'tests' | 'rows'`) so a SQL verdict reads "Returned N rows, expected M" instead of "N of M tests passed", and a refused write reads "Query error" instead of "Compile error" - wording only, the same `RunResponse`/`Verdict.Outcome` values drive both. The complexity panel and the failing-case reveal panel stay gated on `kind === 'code'` deliberately: neither applies to SQL (no complexity target; the row count already is the whole failure signal), so they simply never render rather than rendering a no-op.
- **Tests.** `SqlQueryGraderTest` proves the grader against a fake `SqlRunner` (the `Grader`/`Runner` split, same shape as `AnswerKeyGraderTest`/`TestCaseGraderTest`). `SqlDomainPersistenceTest` (`attempt` package, real Testcontainers Postgres like `AttemptPersistenceTest`) proves every acceptance criterion end to end: solvable through the ordinary `AttemptService.start`/`submit` calls, row order ignored by default but honoured when declared `exact`, column names never compared, a `DROP TABLE`/`UPDATE` refused and the fixture provably intact afterward, the minimal failure signal is a bare row count, and `claimComplexity` rejects a SQL attempt through its ordinary "no complexity check" guard - no SQL-specific branch anywhere in that path.

## Persistence: attempts and submissions

Practice history is durable (issue #15), in the `attempt` package over plain Spring JDBC (`JdbcClient`, not JPA) with the schema owned by Flyway migration `V3__attempts.sql`.
The record is deliberately the schedulers' input (issue #8) and over-captures on purpose, since thin records would cripple that later work.

- An `Attempt` is one sitting with an exercise; a `Submission` is one press of Run within it. Both are person-owned (`user_id` -> `app_user`). `exercise_id` is a plain text id, **not** a foreign key - content lives only in the private repo (issue #4/#14) - so the attempt snapshots `exercise_title`, `domain` and `form` at creation, keeping history readable even with no content clone.
- `AttemptOutcome` is `IN_PROGRESS | SOLVED | ABANDONED | READ`, stored as free text (no DB `CHECK`), so a new outcome is added in the enum alone with no migration - which is how `READ` (a lesson is read, not solved; carries no 0-5 quality, SRS ignores it, readiness counts it) was added ahead of the lesson track that produces it. Abandonment being a recorded outcome, distinct from a never-started absence (no row), is the ticket's core invariant.
- `hints_taken` and `failing_case_revealed` are populated by the judging track (#16, see below); `complexity_claim`/`measured_complexity`/`complexity_claim_correct` are populated by the complexity self-report track (#17, see below - `complexity_claim_correct` is tri-state: true = consistent, false = contradicted, null = no determination). `V4__judging.sql` adds `attempt.reveal_hypothesis` and `submission.runtime_millis`; `V5__explanation.sql` adds `attempt.explanation_requested` (issue #51, see below). None of these are penalised.
- `AttemptService` owns the lifecycle (grading is still delegated to `GraderRegistry`): `start` opens an attempt snapshotting the exercise, `submit` grades + stores a submission and marks the attempt `SOLVED` on the first passing verdict; `abandon`, `takeHint` and `revealFailingCase` act only on an `IN_PROGRESS` attempt (else `IllegalAttemptStateException` -> 409; unknown id -> `AttemptNotFoundException` -> 404, both mapped by `AttemptErrorHandler`). The current user is the single seeded one via the `CurrentUser` seam - the one place to change when auth ever lands.
- The web seam is `AttemptController` (`/api/attempts`: `GET` history, `POST` start, `POST /{id}/submissions|hints|abandon|reveal|explanation`; `reveal` takes `{ submission, hypothesis }`). Grading no longer lives on `ExerciseController` - every run is a persisted submission, so there is no stateless grade path to bypass it. The React editor starts an attempt lazily on the first Run (so glancing never creates an empty row), abandons an unsolved sitting on switch-away, offers the hint ladder and failing-case reveal, and renders a plain history table.

## Judging: withhold by default, hint ladder, reveal on request

The judging behaviour (issue #16, deciding #5) is a training decision, not a UI detail: a failing verdict reports **only the count of failing tests** - `Verdict`/`RunResponse` carry `passed`/`total` and never a case's input, expected or actual. Help is always available, always chosen, always recorded, and **never** reduces a score, blocks completion, or affects the streak.

- Hints are an ordered ladder on the `Exercise` (`List<Hint>`, content-authored, parsed by `ExerciseParser`; empty when absent). `ExerciseView` ships only rung **names**, never bodies - `POST .../hints` discloses one body per call and records the rung reached in `hints_taken`.
- The failing case is disclosed only by `POST .../reveal`, which grades the current `submission` and returns the first failing case (`GraderRegistry.firstFailingCase` -> `TestCaseGrader`; `AnswerKeyGrader` has none). The reveal records `failing_case_revealed` and the ungraded, skippable one-line `reveal_hypothesis` typed first (pedagogy audit). The editor also shows a non-penalised "stuck?" nudge offering the next hint after repeated failures.
- Runtime is `Verdict.runtimeMillis` (measured around `runner.execute`, persisted on the submission), shown for interest only - correctness is pass/fail and runtime is never part of the verdict.
- A check's **explanation** (issue #51) is *not* a hint and lives in its own field: `Exercise.explanation` (nullable, content-authored, parsed by `ExerciseParser`; `selfCheck` needs none - its `modelAnswer` already is one). Unlike a hint it is disclosed *automatically* on a wrong answer (`submit` returns `SubmitResult(submission, explanation)`, populated only on a `FAILED` verdict; `RunResponse.explanation`), and *on request once the sitting has ended* via `POST .../explanation` (`requestExplanation` -> `ExplanationResult`), which records `attempt.explanation_requested` - a confidence signal kept deliberately distinct from `hints_taken` so "took a hint" never blurs into "read why I was wrong". Withhold-by-default is enforced by the API, not just the editor: the request is honoured only from a terminal attempt (`SOLVED` - the "when correct" path - or `ABANDONED`), and an `IN_PROGRESS` attempt is rejected with `IllegalAttemptStateException` (409), so a solver can never read the explanation before answering. `ExerciseView` ships only `hasExplanation`, never the text. Requesting is never penalised. The content format doc for the field lives in the private `swe-prep-content` repo's `README.md`.

## Complexity self-report: claim, target reveal, scaling measurement (issue #17)

After a passing submission, the solver states time and space complexity **before** the authored target is revealed - articulating it is the interview skill - and the time claim is checked by empirically measuring how the submission scales. This is a training decision like judging (#16): a claim is never asserted "correct", only "consistent with measurement" or explicitly inconclusive, because empirical scaling can reliably tell a polynomial-degree change apart but can never separate O(n) from O(n log n).

- Content: `Exercise.complexityCheck` (nullable `ComplexityCheck{targetTime, targetSpace, generator}`, parsed by `ExerciseParser`'s optional `"complexity"` block) is itself optional - an exercise with none skips the whole flow. Within it, `generator` (nullable `InputGenerator`, sealed `Argument` of `ScalingIntArray(min,max)` or `Fixed(value)`, one per signature parameter) is *separately* optional: a target with no generator still asks and reveals, it just skips the empirical check (the ticket's explicit "no generator -> skip without error" criterion). `InputGenerator.generate(size, seed)` synthesises one call's args deterministically, language-neutral like a hand-authored `TestCase.input`.
- The ordering guarantee is structural, not a UI convention: `ExerciseView` ships only `hasComplexityCheck`, never the target. The target is returned from exactly one place, `AttemptService.claimComplexity` (`POST /api/attempts/{id}/complexity`), which records the claim (as `attempt.ComplexityClaim`, serialized into the `complexity_claim` column V3 already had) *before* reading it back - so the target is never sitting in any response the client already holds. Requires `SOLVED` and only once per attempt; measures the submission that solved it (`submit` refuses further calls once `SOLVED`, so that is simply the attempt's last submission).
- `complexity/` package: `ComplexityBucket` collapses the claim vocabulary to five buckets the empirical check can actually discriminate - `CONSTANT`/`LOGARITHMIC` share `SUBLINEAR`, `LINEAR`/`LINEARITHMIC` share `LINEAR` - which is *the* mechanism enforcing the honesty constraint (a linear claim can never be contradicted by a linearithmic measurement, because they are the same bucket). `MeasurementOutcome` is sealed `Skipped | Inconclusive | Conclusive(bucket, exponent)` - only `Conclusive` names a bucket, and even it is never worded "correct" by the caller. `ComplexityClassifier` (pure) fits a log-log linear regression across measured (size, time) points and requires the slope to sit clearly inside a bucket (a fixed margin around each boundary) and above a minimum-reliable-timing floor, else `Inconclusive` - a first-class outcome, not an else-branch.
- `ScalingMeasurer` is the runner's "second execution mode": not a new `Runner` method, but a different generated harness (`LanguageAdapter.generateTimingHarness`) run through the *same* `Runner.execute()`, one call per measured size, so it inherits the exact isolation/timeout every other execution gets. Sizes are ascending; a `TIMEOUT` at one size stops the loop rather than guessing. `ComplexityProperties` (`sweprep.complexity.*`: `sizes`, `warmupRepetitions`, `repetitions`) was tuned **empirically**, not by calculation - real execution surfaced two sharp edges a napkin estimate misses entirely, both load-bearing and worth knowing before touching this:
  - **JIT dead-code elimination.** A trivial loop's return value, if never consumed, can get the whole call eliminated by C2 - the timing harness stashes every call's result into a `static Object sink` field, inside the timed window, specifically to defeat this.
  - **JIT/vectorisation warm-up.** The harness makes `warmupRepetitions` *untimed* calls before any timed one, because a cheap, auto-vectorisable op (e.g. a raw array sum) can show its first few calls an order of magnitude slower than later ones for reasons that have nothing to do with growth rate. The measurer then takes the *median* (not min, not mean) across `repetitions` timed calls per size, to resist the different, one-sided noise shape of shared-box contention (a GC pause, another process) without chasing the vectorisation-driven lows a `min` would. A trivial linear fixture (raw array sum) is still nearly *untimeable* at any practical size even with all this - `ScalingMeasurerTest`'s linear-solution test therefore asserts the weaker, still-meaningful property that measurement never wrongly contradicts it (never lands on `QUADRATIC` or worse) rather than pinning an exact bucket, and uses a heavier-per-element fixture (`HashSet`-backed, not vectorisable). Only the quadratic-catch test asserts an exact bucket, matching the acceptance criterion's own "reliably caught" wording - that is the one case this feature must never miss.
- Frontend: `Practice.tsx`'s `ComplexityPanel`, shown only once `response.kind === 'code' && hasComplexityCheck && solved`; the claim selects post to `.../complexity` and only its response ever populates the revealed target/status state.

## Warm-up reps: the daily core

The ~8-rep, ~4-minute warm-up (issues #3, #9, #18) is the required daily core and shares the exercise model rather than living in a parallel system - reps are just `Form = REP` exercises.
The five rep types map onto existing `Response`/`Grading` pairs, so no new grading machinery was needed: pattern-ID / complexity / fill-in-the-blank / spot-the-bug are `Choice + AnswerKey`; predict-output is `FreeText + AnswerKey`, matched exactly *after normalisation* (`AnswerKeyGrader` strips and collapses internal whitespace on both sides only when the response is `FreeText` - a choice option is only stripped, never whitespace-collapsed, so two options can't collide).
`ResponseView` renders `FreeText` as `kind:"freeText"` for predict-output; a `FreeText + SelfCheck` item still refuses to render (its produce-then-reveal view is T5).
Feedback wires to the *existing* explanation mechanism (#51), not a second one: wrong -> auto-disclose + re-queue; correct -> withheld, one keystroke away, ask recorded.

- **Gating** is `Exercise.derivedFrom` (nullable, content-authored, parsed by `ExerciseParser`, no migration - a content-JSON field): the id of the underlying problem a derived rep falls out of. A derived rep is served only once that problem has been attempted (`AttemptRepository.attemptedExerciseIds`); a pattern-ID rep leaves it null and is available cold. This is the acceptance criterion "available cold vs gated on the problem."
- **Selection** is `reps/WarmupSelector` (pure, no DB/scheduler - fully unit-tested incl. a queue stacked with one topic) wrapped by `WarmupService`, served at `GET /api/reps/warmup` (`RepController`) as an `ExerciseSummary` list. It (1) takes only `REP`s, (2) draws only from active families + always-on `CORE`/`PROFESSIONAL` (untagged content is always-eligible substrate), and (3) gates derived reps. Then it **interleaves** most-common-topic-first (the reorganize-string standard, so the majority topic is never stranded in a tail run), capping consecutive same-topic/same-domain at `sweprep.reps.max-consecutive-same` (default 2); the topic cap is load-bearing and wins over the domain cap when they conflict (an all-one-domain warm-up must still interleave topics). Between otherwise-equal candidates it then prefers the one most **confusable** with the rep just placed, *within the same domain* (issue #39): cross-domain mixing is spacing, not the discrimination win, so it earns no bonus. Confusability ranks below the count key on purpose - most-common-first is what guarantees the cap can always be honoured, so confusability refines ties rather than stranding a majority topic to chase a pair. The confusion relation is `reps/ConfusionPairs` (pure, `derive(failedResponses, catalog)`), a symmetric weighted topic relation built from recorded wrong Choice answers with **no new migration**: on a wrong answer the picked distractor, when it is the answer-key label of some *other* rep, resolves to that rep's topic - the pattern it was confused with. `ConfusionPairService` wires it from `SubmissionRepository.failedResponses` (the `FAILED`-outcome query) + the catalog; a cold history (every install today) derives an empty relation and the selector falls back to family/gating/cap interleaving alone. Config is `RepProperties` (`sweprep.reps.*`, warm-up size and consecutive cap only - the active family set is the user's stored choice, not config; see the "Role families" section below). Due-date selection (issue #20, see "Rep scheduling" below) is a fifth, later-applied filter over this same eligible pool - which reps are *eligible* (this section) and which are *due today* stay two separate, composable concerns.
- **Frontend**: the warm-up runner is `Warmup.tsx`, driven by the session shell (`Session.tsx`, see below); `App` is now a thin wrapper over `Session`. The runner walks the set, re-queues a wrong rep to the end (bounded by `MAX_REQUEUES`), keys its rep-load effect on the current id+position (not the whole queue) so re-queueing does not reload and wipe the feedback, and calls an optional `onComplete` prop when the set is finished (falling back to its own done screen when used standalone). The free-practice editor is `Practice.tsx` (extracted from `App`). Shared fetch helpers live in `src/api.ts`.
- Synthetic fixtures for all five types are in `testsupport/Fixtures` (`patternIdRep`/`complexityRep`/`fillBlankRep`/`predictOutputRep`/`spotBugRep`); each distractor names the misconception it targets - the reviewable gate #42 makes mechanical (see the content-loading section). No real content is committed.

## Role families: the filter you control (issue #40)

The `family` tag becomes a product feature: the user says which roles they are preparing for, and the required daily core follows that choice without hiding anything. The rule is **per-tier, not a global on/off** (design revision t3, section 2.2), and it reuses the warm-up filter rather than adding a parallel one.

- **The choice is a per-user stored set, not config.** The `role` package owns it: `RolePreset` (the closed set of named roles, each expanding to a `Set<Family>`), `RoleRepository` (over `active_family`, Flyway `V7`, one row per active family, `family` free text so a new family needs no migration), and `RoleService` (the single source of the active set). `WarmupService` reads the active families from `RoleService`, **not** from `RepProperties` - there is one family filter, sourced from the user's durable choice. An unset user (no rows) reads as *every selectable family active* (no restriction, the pre-#40 behaviour), so nothing is suppressed before a choice is made. Web seam: `GET /api/role` (presets + current selection), `PUT /api/role {preset}` (`RoleController`); the user picks a role id, the server owns the role->families expansion.
- **Presets, not a checklist.** `RolePreset` is a small honest set led by the captain's AI/ML target: `FULL_STACK_AI_ML` (first, `{BACKEND,FRONTEND,AIML}`), `AI_ML` (first-class standalone), `BACKEND`, `FULL_STACK` (`BACKEND∪FRONTEND` - full-stack is not a family), `FRONTEND`, `EVERYTHING` (all selectable; also how `DATA/DEVOPS/MOBILE/SYSTEMS` are trained). `CORE`/`PROFESSIONAL` are always-on and never part of a preset (the selector adds them). No `family` DB snapshot on the attempt (the issue's optional migration) - not taken; per-family readiness (#45) can derive it from content when needed, and it would duplicate a fact content already holds.
- **What an inactive family means is the tier boundary.** The required warm-up and auto-seeding draw only from active families + always-on; everything stays reachable through Practice/Learn browse and the optional tiers (both list content unfiltered by family). Two exceptions widen the warm-up beyond the strict active set, both via one mechanism - `WarmupSelector`'s new `optedIn` set (a family-filter bypass for specific ids), fed by `WarmupService.optedInReps`:
  - **Reading an inactive-family lesson opts its checks in.** `POST /api/lessons/{id}/read` (`LessonReadService`) records an `AttemptOutcome.READ` attempt; `AttemptRepository.readLessonIds` reads them back and the checks of those lessons join `optedIn`. So the user pulls inactive content in one concept at a time, without flipping a family on. `Lesson.tsx` fires the read best-effort on open.
  - **Deactivating a family leaves already-due reviews intact.** Every *attempted* rep is in `optedIn`, so an in-flight rep whose family later goes inactive stays warm-up-eligible - deactivating stops new seeding without ripping already-due reviews out (review-debt-first, #8). This is the criterion most likely to rot silently; `WarmupServiceTest.deactivatingAFamilyKeepsAnAlreadyAttemptedRepInTheWarmup` guards it directly, alongside the untouched-rep-really-is-suppressed counterpart.
- **`READ` never affects the "learned" signal**, by construction: the competence query is `outcome = 'PASSED'` only (#38), and a `READ` attempt writes no submission, so recording a lesson read can never graduate a check.
- **Frontend**: `RolePicker.tsx` (a preset `<select>` in the session header) is the whole user-facing surface; changing it PUTs the preset and bumps a `roleVersion` key on `Warmup` so the set rebuilds from the new families. It hides nothing and never gates the first rep.

## Session: the daily loop (issue #19)

The three-tier daily session is **the product** (issues #3, #19); everything above is machinery it puts to work. Three tiers, only the first required: the warm-up (~8 reps) completes the day on its own; an optional main exercise (~30 min) follows; then uncapped continuation. The design intent is load-bearing - the small required core exists so a bad, low-motivation day is still finished, so **nothing may give the main exercise gravity that makes declining it feel like failing the day**. Completion is banked the instant the warm-up ends, before the main is ever offered.

- **Day completion is its own durable record**, not derived from attempts: the `session` package over `day_completion` (Flyway `V6`, PK `(user_id, completed_on)`). Chosen over scanning/counting attempts because it is read on every app open (the "seconds to the first rep" criterion) - a single PK lookup - and because a discrete "finished the warm-up" event does not churn as the reps/schedulers evolve, whereas an attempt-counting heuristic would. `SessionService.completeWarmup` marks today idempotently (`ON CONFLICT DO NOTHING`, so a second warm-up never moves the timestamp) and is the **only** path that completes a day; `status()` returns `{dayComplete, completedAt, streak}` and the streak (consecutive days, shown from yesterday before today's rep is in) is derived in-memory from the small per-user date set. `today` comes from an injected `Clock` bean (`SessionConfig`) so tests pin day boundaries. Web seam: `GET /api/session`, `POST /api/session/complete-warmup` (`SessionController`).
- **Domain-agnostic is binding.** No copy, state, or timing may assume an algorithm: the main is the priority scorer's pick across `CHALLENGE`s of *any* domain (`Practice.tsx`, falling back to the first `CHALLENGE`), the landing copy is neutral, and a lesson (issue #46) fits the same shell. Partial main = the existing `abandonIfUnsolved` switch-away path (issue #15), recorded `ABANDONED`; it never touches day completion.
- **Frontend** shell is `Session.tsx` (a `Today`/`Practice` tab pair, later joined by a `Learn` tab for lessons - issue #46/#41): renders the warm-up immediately (status is read in the background, never gating the first rep), and on the warm-up's `onComplete` records the day and shows the day-complete `Landing` (celebrate first, then offer the optional main). `Practice.tsx` is the uncapped main+continuation surface, reachable from the landing or the always-available Practice tab. True "which problem is worth 40 min today" selection is the priority scorer (#8/#21, now built - see "Challenge scheduling" below); `Practice.tsx` calls `GET /api/challenges/next` and only falls back to the static "first available challenge" pick when that call fails or has nothing to offer.
- **An empty warm-up must never leave the day impossible to finish** (issue #19): when today's set comes back empty there are no reps to bank the day, so `Warmup`'s `onEmpty` flips the session into a fallback where solving any one `Practice` exercise (`onSolved`) routes through the same `completeWarmup`. `completeWarmup` stays the only backend path that completes a day; the empty case just gives the frontend a second trigger for it.

## "Learned": the SRS criterion readiness reads (issue #38)

The definition of mastery a scheduler consumes (design revision t3, section 4.1) lives in the `learned` package - a definition and a derivation, not a scheduler itself.
"Learned" is **successive relearning, not an SM-2 ease number**: a clean machine-verdict pass in each of **N distinct spaced sessions** across an **expanding gap ladder**.

- **A session is a distinct calendar day** in the app's `Clock` zone (the same `SessionConfig` clock the session loop reads `today` from, #19) - deliberately *not* a sitting or a `day_completion` row. That is what makes repeated passes in one day count once, so single-session grinding can never graduate an item (the specific failure the ruling rejects) and the criterion survives a user who practises twice in a day.
- `LearnedCriterion.evaluate(passDays, LearnedProperties)` is pure (like `ConfusionPairs`): dedupe to distinct days, then greedily walk them, counting a day as the next session only when its gap from the last counted one clears `gapAfter(counted)`. Graduation (`spacedSessions >= n`) and the relearning cadence (`nextGapDays`, the next expanding rung) both derive from the ladder, never an ease number. `LearnedProperties` (`sweprep.learned.*`, defaults `n=3`, `gapLadder=[1,3,7,14]`, sub-day gaps floored to 1) makes N and the ladder independently configurable; a ladder shorter than N clamps to its last rung. `LearnedService` wires the query + clock zone into the pure criterion and exposes per-exercise and batch (`statesForAll`) state.
- **Read and self-check provably cannot affect the objective signal - structurally, not by convention.** The signal is built only from `SubmissionRepository.cleanPassInstants` / `cleanPassInstantsByExercise` (`outcome = 'PASSED'`). A self-check is never machine-graded: the `submit`/grade path `SelfCheckGrader.grade` *throws* before any row is written, and the produce-then-reveal path (#41, below) does insert a submission but always with `SubmissionOutcome.SELF_RATED`, never `PASSED`. A lesson read is never graded at all. So neither can ever write a `PASSED` row for these queries to return. Domain-agnostic by construction: a SQL check and a coding challenge both graduate the same way. No migration (computed from merged `V3` rows).
- **This criterion feeds readiness reporting (#45), not the due-date queue.** Issue #8 decided *two* schedulers over one record: a due-date SM-2 queue for reps (issue #20, below) and a priority score for challenges (issue #21, "Challenge scheduling" below). Neither reads `LearnedState` to decide what to serve - it stays an independent, informational derivation over the same submission history. See "Rep scheduling" below for why that is a deliberate non-merge, not an oversight.

## Rep scheduling: an SM-2 due-date queue (issue #20)

Reps come back on a schedule instead of being picked at random: due dates advance on a correct answer and shorten on a wrong one, the algorithm sits behind a swappable interface, and a day's warm-up is drawn only from what is actually due. Like `learned`, this is a pure derivation recomputed on read from attempt history, never a mutable row a write path has to keep in sync - no migration.

- **The contract is `scheduler/RepScheduler`** (`schedule(List<Review>) -> RepSchedule`, both pure value types in the same package): nothing outside `scheduler` may know which algorithm answers it. `Sm2Scheduler` (a `@Component`, standard SM-2 - Wozniak 1990, ~50 lines) is the first implementation, not the contract; replacing it later is a bean swap, never a change to `WarmupSelector` or the session flow. `RepSchedule.isDueOn(today)` is `true` for a rep never reviewed (`dueOn == null`, the cold-start answer) or whose computed due date has arrived. Time taken is not a field on `Review` and never was a candidate one - the ticket is explicit that duration is noise, not signal.
- **The 0-5 quality score is `scheduler/ReviewQuality`** (pure, directly unit-tested, not buried in the scheduler arithmetic): a wrong or abandoned rep is `INCORRECT` (0); a correct one is `PERFECT` (5), or `CORRECT_BUT_UNSURE` (3) when the solver requested the explanation despite being right (issue #51's confidence signal, `Attempt.explanationRequested()`). Both 3 and 5 still advance the schedule (a correct answer is a correct answer, the "advance on correct" criterion) but SM-2's easiness delta diverges from the second review on, so the "asked why" streak is trusted with a shorter gap - "weaker" is a diverging trajectory, not a one-off penalty.
- **`reps/RepDueService` wires attempt history into the scheduler**, the same shape as `LearnedService`: `AttemptRepository.repReviews(userId)` reads every terminal (`SOLVED`/`ABANDONED`) `REP`-form attempt - a self-check rep ends `EXPLAINED` instead, so this `outcome IN (...)` filter structurally excludes it with no separate grading-kind check, same shape as `cleanPassInstants`'s `outcome = 'PASSED'` boundary. Multiple reviews of one rep on the same calendar day collapse to the *last* outcome that day, mirroring `LearnedCriterion`'s distinct-session rule - a rep re-queued and answered wrong then right in one warm-up sitting cannot grind extra spaced credit out of a single session. `dueToday(userId, catalog)` returns the due `REP` ids.
- **`WarmupSelector` treats due-date exactly like `optedIn` and gating: a membership filter, applied before interleaving, never an ordering opinion.** A due-aware `select(...)` overload (`WarmupSelectorTest`) narrows the eligible pool to `dueToday` before the existing interleaving/confusability rules (#18, #39) run unchanged - due-date selection and interleaving compose, they never compete. `WarmupService.warmup()` always calls the due-aware overload; the older overloads stay for the tests that only need to prove family/gating/interleaving in isolation.
- **An empty due queue yields an empty warm-up set, not a fallback to "everything eligible".** That set then flows into the existing empty-warm-up handling (issue #19's `onEmpty`, which already covers an empty *eligible* pool) unchanged, so nothing new was needed there - `WarmupSelectorTest.aDayWithNothingDueYieldsAnEmptySetRatherThanFallingBackToEverythingEligible` is the explicit decision-and-test the acceptance criterion asked for.
- **Deliberately independent from `LearnedState`, not reconciled by merging.** `RepDueService` never reads `LearnedCriterion`/`LearnedState`, and vice versa: they are two derivations over the same submission history answering two different questions ("is this due today" vs "has this been retrieved to criterion"), so due-date selection is reconciled *with* the learned criterion (as the ticket asked) by staying orthogonal to it rather than overriding either.

## Challenge scheduling: a priority score, not a due date (issue #21)

The daily main exercise (a 30-40 minute `Challenge`) is picked by score, not by what is owed: `scheduler.ChallengePriority.select(...)` takes every candidate's score and returns the single highest scorer, per decision #8's ruling that a due-date queue (fine for a Rep costing seconds) breaks completely at Challenge scale, where ~90 slots exist against ~75 problems. Pure, no database, the same shape as `Sm2Scheduler`/`LearnedCriterion`.

- **The 0-5 quality score is `scheduler/ChallengeQuality`** - `ReviewQuality`'s sibling, not a reuse of it: a Challenge's judging record carries signals (submission count, help taken, the complexity claim) a Rep's never does, so the two derivations stay separate rather than forcing one input shape to serve both. `PERFECT` (5) requires a clean *first-submission* pass with no hint, no failing-case reveal, and no complexity-claim contradiction (a `null` claim-correct - no check, or an inconclusive measurement - is neutral, never treated as a failure, mirroring issue #17's honesty constraint); anything else that still passed is `WEAK_PASS` (3); a failed or abandoned attempt is `INCORRECT` (1). This is the "attempt records collapse into a 0-5 quality score" acceptance criterion, and the consolidation point for a future third scheduler: extract a shared strategy interface then, not before.
- **The score itself is `scheduler/ChallengePriority`**, fed `scheduler.ChallengeCandidate`s (an exercise id, its own `Review` history, and a topic-coverage fraction - never raw attempt fields). Two signals from decision #8's list merge into one *overdue* term rather than staying separate: `overdue = daysSinceLastAttempt - requiredGap`, where `requiredGap` comes from `ChallengeSchedulerProperties.gapAfter(cleanPasses)` - an expanding ladder (default `[1, 3, 14, 90]` days) indexed by how many distinct days the Challenge has earned a `PERFECT` pass. That ladder's last rung is deliberately months-scale: "a problem passed cleanly three times earns an interval of months" (issue #21) falls out of `overdue` going deeply negative once `cleanPasses` hits the ladder's tail, which is *why* a mastered problem stops scoring competitively without ever being excluded - retirement, not removal, is an emergent property of the score, not a special case. A second, independent term (`5 - lastQuality`) rewards a badly-went last attempt directly, and a third rewards an under-covered topic.
- **Two gates sit outside the score, deliberately, because "never selected" and "capped" cannot be soft preferences a large enough bonus might still outscore into selection:** the minimum-interval floor (`ChallengeSchedulerProperties.minIntervalDays`, default 2 - a gap of *exactly* two days is excluded, matching the ticket's own "two days ago is memorisation" wording) and the weekly new-introduction cap (`maxNewPerWeek`, default 3, checked only against a *never-attempted* candidate - `reviews.isEmpty()`). Both return `OptionalDouble.empty()` from `ChallengePriority.scoreOf`, not a low score. "Review debt first, new problems second" is not a separate priority lane: a never-attempted Challenge scores from a flat, deliberately low `newProblemBaseline` (default 1.0) plus its own coverage bonus, so a genuinely weak *due* Challenge's overdue and badness terms win the ordinary score comparison rather than needing an if/else.
- **`challenge/ChallengeService` wires attempt history into the scorer**, the same shape as `LearnedService`/`RepDueService`: `AttemptRepository.challengeReviews(userId)` reads every terminal `CHALLENGE`-form attempt (`outcome IN ('SOLVED', 'ABANDONED', 'EXPLAINED')`, one wider than `repReviews`'s `('SOLVED', 'ABANDONED')` because a self-check challenge - issue #41's produce-then-reveal-then-self-rate, the `AIML` flagship main - ends `EXPLAINED`, never `SOLVED`/`ABANDONED`, and omitting it would leave such a challenge permanently invisible to the scorer, `reviews.isEmpty()` forever, silently defeating the minimum-interval floor for it and violating AC #2; `ChallengeAttemptRow` therefore carries the raw `AttemptOutcome`, not a bare `solved` boolean, so `ABANDONED` and `EXPLAINED` stay distinguishable), `ChallengeService.qualityOf` gives an `EXPLAINED` row a fixed `ChallengeQuality.WEAK_PASS` **purely as a scheduling-timing signal** - just enough for the floor and overdue tracking to register the attempt happened, and explicitly never to be read as, or feed, an objective machine-verdict competence score (`LearnedCriterion` and the readiness "solved cold" axis stay structurally blind to a self-rated attempt, reading only `outcome = 'PASSED'`/`'SOLVED'` rows). `SubmissionRepository.countsForAttempts` supplies the per-attempt submission count `ChallengeQuality` needs, `AttemptRepository.solvedColdExerciseIds` (issue #45's honest "solved without help" signal, reused rather than a new query) drives topic coverage across the `CHALLENGE` catalog, and `AttemptRepository.firstChallengeAttemptDates` drives the weekly cap's count (a Monday-start calendar week in the session clock's zone). `GET /api/challenges/next` (`ChallengeController`) serves the pick as an `ExerciseSummary`, `null` when nothing is currently selectable; `Practice.tsx` calls it to choose the main exercise and falls back to its old static "first `CHALLENGE`" pick only if the call fails or genuinely has nothing to offer.
- **Deliberately independent from `LearnedState`**, the same non-merge as `RepDueService`: readiness's "learned" criterion (issue #38, `n=3` spaced sessions over a `[1, 3, 7, 14]`-day ladder) and the priority scorer's retirement ladder answer different questions - "is this item objectively mastered for the readiness picture" versus "how long should a Challenge slot leave this one alone" - and are tuned independently on purpose, never sharing one `LearnedProperties` config.

## Production practice: self-graded explain and lesson prompts (issue #41)

The required daily core trains recognition; production is made first-class in the *optional* tiers and in the lesson (design revision t3, sections 1.1/4.3). The narrowed ruling is **no *machine-graded* free text** - eliciting it is fine, grading it is not - so this is produce-then-reveal, never a machine verdict.

- **`Submission.outcome` is a `SubmissionOutcome`, a superset of `Verdict.Outcome`** (`attempt` package): the five machine outcomes plus `SELF_RATED`. Keeping `SELF_RATED` out of `Verdict.Outcome` is the type-level half of the boundary - a self-check leaves a record that cannot be mistaken for a verdict, and the competence query (`outcome = 'PASSED'`) is structurally blind to it. `SubmissionOutcome.of(Verdict.Outcome)` maps machine verdicts one-for-one.
- **The self-check lifecycle is `AttemptService.revealSelfCheck` then `rateSelfCheck`** (endpoints `POST /api/attempts/{id}/self-check/reveal` and `.../self-check/rating`). Reveal requires a `Grading.SelfCheck` exercise and non-blank produced text (else 400), inserts the produced text frozen as a `SELF_RATED` submission *before* returning the model answer (via `SelfCheckGrader.reveal`), then rating stamps the `SelfRating` (`NAILED_IT`/`PARTIAL`/`MISSED`) onto that submission's `detail` and ends the attempt `EXPLAINED`. Freezing the text at reveal is why a self-rating after peeking is distinguishable in the record; ending `EXPLAINED` on rating makes it irreversible. New `AttemptOutcome.EXPLAINED` is code-only (free-text stored); self-rating storage reuses `detail` - no migration.
- **The warm-up excludes self-check items** (`WarmupSelector.warmupGradable`) so the required core stays recognition-and-fast and unchanged in length, even if an explain item is authored as a `REP`. Explain items belong in the optional main (a `CHALLENGE`, the `AIML` flagship) and continuation.
- **Rendering**: `ResponseView.selfCheck()` (kind `"selfCheck"`, from `FreeText` + `SelfCheck`) is distinct from the machine-graded `freeText` (predict-output); the model answer is never in `ExerciseView`. Frontend produce-then-reveal-then-rate lives in `Practice.tsx` (`SelfCheckView`).
- **Lessons carry ungraded self-explanation prompts**: `Lesson.prompts` (`List<SelfExplainPrompt>`, `{prompt, modelAnswer}`, parsed by `LessonParser`, optional, no migration - content JSON). A lesson stays `READ`: no response, no grader, no attempt. Served by `LessonController` (`GET /api/lessons`, `/api/lessons/{id}` -> `LessonView`, over `ContentCatalog`); the prompt reveal is client-side in `Lesson.tsx` (a "Learn" tab in `Session.tsx`), so the model answer *is* shipped (nothing to protect - not a verdict).
- **Test-infra sharp edge**: `FileExerciseCatalog` is one bean implementing both `ExerciseCatalog` and `ContentCatalog`. A `@SpringBootTest` that `@MockitoBean`s `ExerciseCatalog` splits that bean, so `LessonController`'s `ContentCatalog` is unsatisfied and the whole context fails to load - such tests must also `@MockitoBean private ContentCatalog`.

## Readiness: the honest progress surface (issue #45)

The map's "no invented currency" ruling (issue #7) is completed, not just defended, by giving the user something real to look at instead: the `readiness` package (`ReadinessService`, served by `GET /api/readiness`) derives the whole picture on read from data that already exists, the same shape as `LearnedService`/`RepDueService` - no new table, no mutable summary row.

- **Two objective competence axes, machine-verdict-only by construction.** `checksToCriterion` reads `LearnedService.statesForAll` (itself built only from `outcome = 'PASSED'` rows, issue #38) over every `Form.REP` exercise in the catalog. `solvedCold` reads a new `AttemptRepository.solvedColdExerciseIds` query (`form = 'CHALLENGE' AND outcome = 'SOLVED' AND hints_taken = 0 AND failing_case_revealed = false`) over every `Form.CHALLENGE` exercise - "solved" alone is not enough, since help taken is already tracked (issue #16) and this axis is only honest if it means solved *without* it. Both travel as a `Progress(achieved, total)` record, never a percentage-only or single score, per the map's currency ruling.
- **`conceptsCovered` is a third, independent axis**: Lessons read (`AttemptRepository.readLessonIds`) over every `Lesson` in the catalog - exactly the "readiness picture counts it" the `AttemptOutcome.READ` javadoc anticipated back in issue #40. It shares no query and no code path with the two competence axes above.
- **The self-check "explained N concepts" count is structurally incapable of inflating the objective axes.** It reads a fourth new query, `AttemptRepository.explainedExerciseIds` (`outcome = 'EXPLAINED'`), and travels as a bare `int`, not a `Progress` against any catalog total - there is no field for it to be added into. This mirrors the design revision t3 section 1.1 boundary the same way `LearnedCriterion` and `cleanPassInstants` already do for the SRS.
- **Per-family breakdown** (`FamilyReadiness`) reruns both competence axes once per `Family`, scoped by `Exercise.family().contains(family)` read live from `ContentCatalog` - the optional `attempt.family` snapshot design revision t3 costed out was not taken (per the role-families section above), so a family with no content in the local clone reports `0/0` rather than being silently omitted or estimated.
- **Frontend**: `Readiness.tsx` is a top-level tab in `Session.tsx` (alongside Today/Practice/Learn, not tucked under Practice), and the day-complete `Landing` screen links straight into it - the two ways the ticket's "primary surface, not a secondary screen" criterion is made concrete rather than asserted. The self-check count renders in a visually distinct dashed box with its own "never added into the checks above" note; the streak line (when shown here) reuses `SessionStatus.streak` and is worded descriptively, never as a loss, matching `DayBadge`/`Landing` (issue #19).

## Habit layer: solution auto-commit, shaky/stale topics, and streak repair (issue #22)

The last three legs of decision issue #7's no-invented-currency resolution. All three are additive over existing machinery - no invented currency was added anywhere, per the ruling's hard boundary.

- **Solution auto-commit.** `commit/SolutionCommitService` writes a solved `Response.Code` exercise's real source to the *same* private `swe-prep-content` clone `sweprep.content.path` already points at (a `learner-solutions/` subdirectory - `sweprep.commit.*` `solutions-dir` config; deliberately **not** `solutions/`, which the content-authoring tool (issue #24's `ContentWriter`/`AuthorContentCli`) already owns for authored reference solutions, so a learner solution can never overwrite or commit over one - decision #7 is explicit that solutions live in the content repo, not a third one), commits it via JGit (a pure-Java git implementation, needed so tests never require a `git` binary or touch a real remote - `SolutionCommitServiceTest` proves the whole flow, including push, against a throwaway local bare repo fixture), then pushes so the commit actually reaches the contribution graph. `AttemptService.submit` calls it only on the submission that *freshly* solves an attempt (the DB write happens first, in its own short transaction via the split `recordSubmission`/`submit` - git I/O runs after, never inside the DB transaction, the same discipline `claimComplexity` uses for measurement) and only for `Response.Code` exercises - a picked option or a predicted value is not a "solution" artifact. **No commit without real work** is enforced three ways: the response-kind gate above, the fresh-solve-only call site, and `CommitCommand.setAllowEmpty(false)` (resubmitting byte-identical code is rejected - as `EmptyCommitException` on the normal path or `JGitInternalException` carrying the same "no changes" case through `setOnly`'s temporary-index path - and reported as a skip, never an empty commit). Every failure mode (missing clone, no git repo, push unreachable) degrades to `SolutionCommitResult.skipped`/`committedButPushFailed`, logged and swallowed - this must never throw, since it runs after grading has already succeeded. `SubmitResult.solutionCommitted` (and `RunResponse.solutionCommitted`) surface whether it actually happened, honest confirmation rather than an invented "committed!" toast that could lie.
- **Shaky and stale topics** extend the readiness picture (issue #45) with two topic-level axes decision #7's own mockup named ("Shaky: graphs, intervals" / "Not touched in 3 weeks: dynamic programming"), computed by the pure `readiness/TopicReadinessCalculator` from data `ReadinessService` already reads - no new query beyond `AttemptRepository.lastAttemptDates` (max `started_at` per exercise, any outcome). Both share one boundary: a topic never attempted is "not covered" (`checksToCriterion`'s job), never shaky or stale - a topic can only be struggling or going cold on something it has actually been tried on. `shakyTopics` is scoped to `REP`-form exercises (matching `checksToCriterion`'s own scope): a topic is flagged when its learned ratio across every REP tagged with it falls below `sweprep.readiness.shaky-threshold` (default 0.5). `staleTopics` spans both forms and flags a topic whose most recently attempted exercise was opened `sweprep.readiness.stale-after-days` (default 14) or more days ago, sorted most-stale-first.
- **The capped repair mechanic** is `session/StreakCalculator` (pure, unit-tested with fixed dates - no wall-clock dependency, unlike the Testcontainers persistence tests which necessarily use the real clock and so only smoke-test the wiring, never exact repair-count arithmetic that could flip on a calendar-month boundary). A "double session" is the required warm-up plus a solved `CHALLENGE` on the same day - the existing three-tier session model (issue #19) already gives this a real meaning, so no new "session count" concept was invented. Walking backward from today, a missed day is bridged (the streak continues through it, but the missed day itself is never counted as practised) exactly when the day right after it was both completed *and* a solved-challenge day. The monthly cap (`sweprep.streak.max-repairs-per-month`, default 2) restricts only repairs whose missed day falls in the current calendar month - a repair from an earlier month is already-spent history and is never retroactively invalidated. Nothing is ever written to record a repair: like `LearnedService`, it is fully re-derived from `day_completion` and solved-`CHALLENGE` attempts (a new `AttemptRepository.challengeSolvedInstants` query) on every read. `SessionStatus` gained `repairsRemainingThisMonth` (a plain count) and `repairPending` (a plain boolean, true when solving a challenge today would repair a currently-broken streak) - both rendered as honest nudges in `DayBadge`, never as a loss.

## Daily cue: an outside-the-JVM scheduled notification (issue #23)

The "scheduled surfacing" leg of the streak decision (issue #7) is a standalone shell mechanism, not backend code: it needed no new endpoint, since `GET /api/session` (issue #19's `SessionService.status()`) already answers "is today done" from the real session record.

- `scripts/daily-cue.sh` calls that endpoint and decides `notify`/`skip` (a pure, sourced-and-unit-tested `decide()` function); on `notify` it shells out to a swappable notify command (`SWEPREP_DAILY_CUE_NOTIFY_CMD`, default `notify-send`) rather than hardcoding a delivery channel, since what actually pops a notification varies by machine (desktop Linux, a WSL host with no notification daemon, etc.).
- `scripts/daily-cue/` holds the systemd user `.service`/`.timer` unit templates (`__REPO_PATH__`/`__TIME__` placeholders) and `install.sh`, which fills them in and runs `systemctl --user enable --now` for the current account - the same scheduled-user-service mechanism the app's own autostart already uses (decision issue #2), never a second one. `Persistent=true` on the timer plus `systemctl --user enable` is what survives a reboot; `install.sh` also checks and warns if `loginctl enable-linger` isn't set, since without it neither this timer nor the app's own autostart unit run before a login session exists.
- `scripts/daily-cue.test.sh` (wired into `test.sh`) exercises the real script end to end by shadowing `curl` on `PATH` and `notify-send` via the env var, never by testing a copy - same discipline as `check-no-content.test.sh`.
- Installing is a deploy step for whoever operates the machine (`scripts/daily-cue/install.sh --time HH:MM`); nothing in this repo runs it automatically.
